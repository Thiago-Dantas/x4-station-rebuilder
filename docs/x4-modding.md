## What happens when the player confirms a changed plan (verified, files)
Source: `ui/addons/ego_detailmonitor/menu_station_configuration.lua`.
1. While the player edits, the menu asks the engine what the edit changes:
   - `GetNumRemovedConstructionPlanModules2(holomap, station, &newIndex, usestoredplan=false, &numChangedIndices, checkupgrades=true)` and `GetRemovedConstructionPlanModules2(buf, n, changedIndices, &numChangedIndices)` (line ~3490) return **the component ids of the modules that will be removed**, the plan indices that are new or changed, and the index of the first new module.
   - `GetModuleRecycledResources(moduleid)` returns **what each removed module gives back** (vanilla refund). The plan view lists them under "Removed Modules" (text 1001/7964), new and changed ones under "Planned and Changed Modules" (1001/7963).
   - Unchanged modules are the plan entries whose index is not in `changedIndices`. **The engine decides the matching**; no FFI call or MD action sets which existing module a plan entry is (see S1 below).
2. **Confirm** (`menu.buttonConfirm`, line 954) is one engine call: `SetConstructionSequenceFromConstructionMap(station, holomap)`. Nothing else in Lua.
3. The engine adds a build task to the station's build storage. The build storage's AI script `aiscripts/build.buildstorage.xml` handles `event_build_added` and calls `process_build`.
4. Removed modules are **recycled by the builder over time**: the build processor has `recyclingcomponents` (Lua `GetComponentData(processor, "recyclingcomponents")`), and the plan view shows a countdown for removed modules (`menu.getBuildProgress`, line 4958). So there is time between confirm and a module disappearing (how long: test B6).

Vanilla intent (tutorial text 10190/26073): "The builder ship will then deconstruct the module, placing the recovered resources back in the Build Storage."

### Hypothesis: why materials seem to vanish (to check in B2/B3)
The menu counts removed modules' recycled resources toward the first new module's needs when that module doesn't exist yet (lines 3569–3584). If the build processor does the same, recycled wares go straight into new modules and never show up in build storage. Together with a partial refund (`recyclingwares.max` may be below the build cost), a full replacement would look like most materials disappeared.

The map menu's station info also shows build storage **space used / capacity per transport type** (`GetCargoTransportTypes(buildstorage, …)`, `menu_map.lua` ~14727). **Wares flow one way (verified, files):** a station's own trade script sells wares **to** its build storage for free (`aiscripts/trade.station.xml` ~763: `find_sell_offer seller=station buyer=station.buildstorage`; "Trades between a station and its build storage do not require money"). Nothing in the scripts moves wares from build storage back to the station or sells them; `RemoveBuildPlot2(station, removebuildstoragecargo)` only clears them. So wares the build doesn't need probably stay in build storage (OD-10).

## S1: keeping unchanged modules (findings so far)
- The engine matches existing modules to plan entries; Lua only reads the result (`changedIndices`). No FFI function or MD action to bind a plan entry to an existing module was found. Modules are tied to plan entries by entry id (`defensible.planmodule.{$constructionplanentryid}`).
- Loading a library plan onto a station is `ShowConstructionMap(holomap, station, planid, restore=false)`. A saved plan's XML has no component ids (macro, connection, predecessor, offset only).
- **B1(a) verified (run 19, 2026-10-16, log `research/logs/run-20261016-103742.txt`):** scenario `b1` on a new `tutorial_station` (OIY-653, 7 modules), protections off. The build menu saved the live plan (`player_1792158032`, name `esr b1`) and loaded it back. Before the save the open menu was already 7 entries, 7 with a component, 0 removed. After the load, immediate and 2 s later: the same. Confirm agreed: `CONFIRM summary unchanged=7 changed=0 (existing 0) removed=0`, and `PLAN` kept all 7 entry ids (`0x483`–`0x489`) on the existing modules, 0 new, 0 removed, price 0. Three seconds later the station was still 7 operational modules and no build was in progress. So an identical layout loaded from a plan file is matched onto the existing modules. The saved file is what made that clear: it stores positions, not component ids, and the engine still kept every module. Loading a *different* plan still replaces everything (the 427-module replacement, unchanged 0 / removed 427). Build order (B1b) and moving one module (B1c) are not tested yet.
- **B1(b) so far (run 20, 2026-10-16, log `research/logs/run-20261016-104737.txt`), not finished:** plan `player_1792159001` is that same layout with the two energy-cell modules swapped in sequence order (open order x=−884 then 1916; after load, 1916 then −884). The build menu still said 7 entries, 7 with a component, removed 0, changed 0 (`CONFIRM summary unchanged=7 removed=0`). Confirm then added build `0x8578` at price 0, queued, not in progress. Its sequence entries have new ids (`0x23f3`–`0x23f9`) that `planmodule` does not map, so the diag's own removed list says 7. That list is not the engine's: it is "no entry id points at this module yet". At that instant and 3 s later every module was still operational and none were under construction. The scenario quit while the build was still queued, so it does not say whether that build later dismantles the station.
- If a moved plan drops modules, a script that wants to keep them would have to apply a sequence that still carries the station's entry ids (`apply_construction_sequence` / `add_build_to_expand_station`). MD cannot reorder entries. The map FFI (`ShuffleMapConstructionPlan2`, `RemoveItemFromConstructionMap2`, `AddMacroToConstructionMap`) is the other place a build order can change.

## How the engine computes module refunds (X4.exe 9.00, reverse engineered 2026-10-15)
Static analysis of `X4.exe` (sha256 19750a65…6891) with capstone and Ghidra 12.1.4 (headless, decompiling single functions without auto-analysis; REA's full Ghidra analysis timed out on the 55 MB binary). Addresses are virtual addresses in that build.
- **Observed (static):** `GetModuleRecycledResources` / `GetNumModuleRecycledResources` (exports at `0x1401d2a10` / `0x1401d5fd0`) compute nothing; they read a cache (tree keyed by module id at `0x14391e440`, valid while the build map is open) that only `PrepareBuildSequenceResources2` fills, through `FUN_140394e90`. For every module the plan change removes (class id `0x73` = `module`), it builds a component list = the module itself plus every descendant whose class is `destructible` (`0x24`, with subclasses; filter object `0x1431b5030`), not descending into `container` (`0x6f`) or `ship` (`0x75`) subtrees (filter `0x1431bb980`). `FUN_1403e7bb0` then adds, for each listed component (skipping one component state), the resources of its ware's production method for the station's build method (`FUN_1408fa420`; falls back to `default`), and `FUN_14051cf50` scales by the components' hull fraction. Class ids come from the engine's class-name table (121 names, pointer array `0x1422c6790`). In the class tree `turret → weapon → destructible` and `shieldgenerator → destructible` (scriptproperties.xml).
- So the code path **is built to include** turrets and shields on a removed module.
- **Observed (runtime, unequipped modules):** in the user's replacement all 13 removed piers reported the same refund (169 / 1250 / 348 = the pier's recipe), and build storage received exactly that, without equipment wares. **Corrected 2026-10-16:** the turrets and shields nested under two of those piers belong to **docked ships** (save: their direct parent is a `ship_l`), which the engine's exclude filter skips (`container`, `ship`). So this matches the code and says nothing about station equipment.
- **Observed (runtime, equipped modules, verified 2026-10-16, log `research/logs/manual-2026-10-16-equipment-test.txt`):** the user removed one defence disc and one container storage S, one at a time, through the build menu, protections off. `GetModuleRecycledResources` equalled the module recipe plus the recipes of the turrets and shields the MD logger listed on that module (`PLAN removed-equipment`; recipes from `ego_dlc_terran/libraries/wares.xml`). Build storage received that amount in full once recycling finished. Hull was 100 % (integer match); `FUN_14051cf50` would scale a damaged part down.
  - **Defence disc** `defence_ter_disc_01_macro` on Getsu Fune Defence Platform I: recipe 57 computronic substrate / 419 energy cells / 117 silicon carbide. Equipment: 4× `shield_ter_l_standard_01_mk3`, 8× `turret_ter_l_beam_01_mk1`, 16× `turret_ter_m_laser_02_mk1`, 8× `shield_ter_m_standard_02_mk3`. Engine refund = recipe + equipment = 609 / 57 587 / 7 316 metallic microlattice / 1 089. Build storage before `{computronicsubstrate=2}`; after `{energycells=57587, computronicsubstrate=611, metallicmicrolattice=7316, siliconcarbide=1089}` (delta = engine refund).
  - **Container storage S** `storage_ter_s_container_01_macro` on Getsu Fune Defense: recipe 14 / 103 / 29. Equipment: 4× `shield_ter_m_standard_02_mk3`, 8× `turret_ter_m_beam_02_mk1`. Engine refund = 194 / 17 515 / 2 336 / 337. The same confirm also changed one disc (needs = one L shield mk3: 40 / 5 286 / 563 / 79). Build storage after = before + refund − those needs, exact.
- **Conclusion (verified in game):** vanilla refunds **100 %** of a removed module's recipe **and** of the turrets and shields mounted on it (undamaged). Docked ships' equipment is not included. Run 14's empty `upgradeplan` on the CVL-296 piers is consistent with those piers having no station equipment.
- **Consequence for the mod (D-17):** do not add an equipment refund. `esr_refund.xml` stays log-only; adding the equipment cost would double vanilla.

## Workforce grace and leave rate (verified in game, run 15, 2026-10-16)
Log `research/logs/run-20261016-090809.txt`. Scenario `grace` on `save_010`: a new `tutorial_station`, workforce protection on, `$GraceHours` set to 0.1 and `$LeaveRate` to 20 by the harness (the save's stored leave rate was 10; the `MAIN tracking` line shows `grace=0.1h leave=20`). The Argon S habitat was removed and not rebuilt. 250 workers were held one second after the plan change, when capacity hit 0. The build finished about 60 s later; the pool stayed tracked.

- **Grace (verified):** the pool stayed at 250 on every sample through the last one inside the grace period (game time 362681.80; grace end 362704.209, exactly 360 s after the loss). The first sample after that (362715.02) was 249.539.
- **Leave rate (verified):** 15 min of game time after the grace period the pool was 237.314. The one-step form of 20 %/h over that 0.254 h, applied to the 250, predicts 237.303. Between the first post-grace sample and the end the continuous rate is 20.0 %/h of the workers still held. The sweep applies it every 30 s as `held − held × rate × elapsed hours`, so the first tick after the grace period also covers the sweep interval that started inside the grace period (here 0.46 workers).
- **Time warp (the harness does not start it):** `set_timewarp_factor factor="6"` errors with `Evaluated value '6' is not of type time` (run 15). The factor is a time (game seconds per real second; the schema caps it at 6), and the properties are `player.timewarp.*`, not a global `timewarp`. `factor="6s"` is accepted and the property then reads `factor=6` (runs 16–18). That stores the rate. It does **not** start SETA. `timewarp.active=1` in those logs is not the clock running: the player turned SETA on with the key on every test (2026-10-16). Vanilla starts it as a player activity (`md/modes.xml` `Mode_SETA`, the SETA key: `signal_objects` `'startactivity'` / `activity.seta`, then `set_player_activity`), and that cue gives up unless `player.isincontrolposition` and `player.timewarp.available`. **Future tests:** do not wait on the harness to enable time warp, and do not treat `active=1 factor=6` as 6×. The person at the machine presses the SETA key. A script has started SETA only when a run shows `player.activity` = `activity.seta` without that keypress and the wall clock is near 6×.

## MD state in existing saves (verified 2026-10-16, run 13)
A root cue without conditions runs once; in a save where it already ran under an older script version it does not run again, so variables added to it later never exist (`Property lookup failed: md.ESR_Refund.State.$Loadouts`). Rule for this mod: every state table is also created where it is used (`do_if not …?` → `set_value … table[]`), and timer conditions read state with `@`.

## Protections, first version (2026-10-15; design, untested in game)
Code in `extension/md/`; all off by default in dev builds (D-14). Workflow: [workflow-protections-v1.md](../tasks/workflow-protections-v1.md).
- **Tracker** (`esr_main.xml`): `event_player_build_added` with `isexpansion` on a player station starts tracking that station and its build. A sweep runs at once and every 30 s. **Doomed modules** come from the engine itself when the plan change was confirmed in the build menu: `ui/esr_confirm.lua` wraps Confirm and sends `{station, removed module…}` (the menu's `removedModules`, i.e. `GetRemovedConstructionPlanModules2`) with `AddUITriggeredEvent("StationConfigurationMenu", "esr_confirm", list)`; `ESR_Main.OnConfirm` reads it from `event.param3` (schema: "param3 = screen parameters"; vanilla passes Lua tables the same way, e.g. `"modinstalled"`, and MD indexes them as lists). Without that list (plan changed some other way), doomed = station modules that no entry of the build's `constructionsequence` maps to through `planmodule.{entry.id}` (hypothesis: kept modules keep their entry ids; B1). The first sweep with both logs `MAIN COMPARE` (counts only in one list), which answers B1 as a side effect.
- **Ships** (`esr_ships.xml`): docked ships (`dockingbay.docked`) at doomed modules. Player ships with a pilot get `create_order id='MoveWait' immediate` to a `get_safe_pos` spot 1–2 station sizes away (`timeout 0s` = wait there until given new orders; vanilla does the same in `factionlogic_economy.xml`). Other owners' ships get `request_undocking`. No pilot, or still docked 60 s later: `warp` to that spot. Skipped: the player's own ship, units, mass traffic.
- **Cargo** (`esr_cargo.xml`): per transport tag, `station.cargo.capacity.{tag}` minus the doomed storage modules' `macro.cargo.capacity.{tag}`; used volume (amount × `ware.volume`) above that moves to build storage (`remove_cargo` then `add_cargo`; put back if build storage refuses), spread over that tag's wares.
- **Refund** (`esr_refund.xml`, log-only, D-17): vanilla already returns 100 % of each removed module's recipe plus mounted turrets and shields. The script still prices the loadout the build menu sent at Confirm (`esr_equipment`) and logs it when the module is gone; it adds nothing to build storage.
- **Workforce** (`esr_workforce.xml`): per race, a drop while capacity is below the previous amount (`prev − max(now, capacity)`) goes into a held pool; `add_workforce` returns it as capacity frees up; after the grace period the pool shrinks by the leave-rate setting each sweep.
- **Settings** (`esr_main.xml`): stored in `md.ESR_Main.Settings`; registered with SirNukes' `md.Simple_Menu_Options.Register_Option` on its `Reloaded` signal (buttons 0/1, sliders with `$args = table[$min, $max, $step, $suffix]`; the callback gets `$echo` and `$value`). Known limit: `Settings` is a root cue without conditions, so a setting added in a later version needs a cue `version` bump or a patch to get its default into existing saves.
